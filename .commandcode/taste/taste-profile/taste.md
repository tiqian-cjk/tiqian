# Taste profile
- Expects replies in plain, complete-sentence Chinese: no telegraphic phrasing, no unexplained jargon, no self-invented compound words, no vague cross-references; every term must be defined at first use. Confidence: 0.98
- When two codebases or two versions of the same code coexist, name the exact object of every statement (which repo, which path, which file, which side a change targets); ambiguity about what an action applies to is unacceptable. Confidence: 0.9
- Answer the direct question first, then explain; delivery reports open with what the thing is and does, and implementation detail is given only on request; explanations must go deep enough that even basic vocabulary (e.g., require vs must, default parameter) is spelled out rather than assumed. Confidence: 0.88
- Prefers minimal-invasion changes: never propose or perform broad refactors that break existing code compatibility as a side effect of new work, and never start executing a large change without naming the target and getting agreement first. Confidence: 0.85
- Performance is a hard requirement with zero exemptions: "not a hot path" is never an acceptable excuse, output-size or diff-size changes never justify slower code, and the optimal design must be argued down to per-platform detail (compile-time resolution, native constructs, inline expansion, frozen singletons, constant loop bounds, zero per-evaluation allocation). Confidence: 0.97
- Every new feature in a multi-target tool must behave consistently across ALL supported target languages, verified by cross-platform consistency tests; single-target ("Kotlin only") implementations are rejected outright. Confidence: 0.96
- Expects deep, exhaustive per-platform analysis before writing a spec; workflow is spec first (covering every target), then implementation, with no shortcuts. Confidence: 0.88
- Correctness per the governing standard wins over parity with an existing wrong implementation: never preserve a bug just to keep golden output or tests identical; a behavior fix may legitimately change goldens. Confidence: 0.85
- Data-derived code should be built with compile-time macros (e.g., Haxe @:build macros), never with standalone codegen pipelines that emit source files. Confidence: 0.85
- Exceptions should carry source-identifying names (project-specific prefixes rather than generic builtin names) so callers can tell where an error came from and can fall back; error attribution should be cross-layer. Confidence: 0.8
- Comparison and verification tooling may encode explicit, documented equivalence rules (e.g., treating two exception names as equal on trace lines) — golden comparison is not purely mechanical and can special-case principled differences. Confidence: 0.8
- Script-automate repetitive multi-file loops (generate → swap → verify) instead of doing them manually one file at a time; manual one-by-one work across many files is considered inefficient. Confidence: 0.88
- Merge completed batches into the main branch promptly and incrementally; never accumulate work for a single big merge at the end (a /tmp worktree can be reclaimed at any time). Confidence: 0.9
- Tests must be serialized through a central locking script and never run in parallel; parallelism is only for independent implementation lanes and dispatched agents. Confidence: 0.85
- Doc-style and word checks should ban whole classes of vocabulary (e.g., the entire "-level"/"X级" suffix class) rather than enumerating individual banned compounds one at a time ("whack-a-mole"). Confidence: 0.85
- Commits: autonomous single-line conventional commits are fine during authorized work, but no Co-Authored-By or any attribution trailer is ever permitted. Confidence: 0.9
- Compiler/tool features are spec-first and must be merged back: change the compiler only with its spec updated, and land both in the repo the tool lives in before downstream consumers upgrade to it. Confidence: 0.85
